# Задание: Система аутентификации и авторизации

## Описание проекта

Необходимо реализовать backend-приложение с собственной системой аутентификации и авторизации. Приложение не должно быть полностью основано на возможностях фреймворков, идущих «из коробки».

## Основная цель

Разработка собственной системы разграничения доступа к ресурсам, включая:
- Проектирование схемы базы данных
- Описание составляющих, отражающих правила доступа
- Реализацию API для управления правами

## Функциональные требования

### 1. Взаимодействие с пользователем

Система должна обеспечивать полный цикл работы с пользователями:

- **Регистрация**: ввод имени, фамилии, отчества, email, пароля с подтверждением
- **Авторизация**: вход по email и паролю
- **Выход**: завершение сессии пользователя
- **Обновление профиля**: редактирование личных данных
- **Удаление аккаунта**: мягкое удаление (soft delete) — установка флага `is_active=False`, выход из системы, невозможность повторного входа

После авторизации система должна идентифицировать пользователя при последующих запросах.

### 2. Система разграничения прав доступа (RBAC)

Требуется реализовать собственную Role-Based Access Control систему:

#### Структура базы данных

- **Users** — пользователи системы
- **Roles** — роли (Admin, Manager, User, Guest и т.д.)
- **Resources** — защищаемые ресурсы (documents, reports, settings и т.п.)
- **Permissions** — разрешения (view, create, update, delete, export)
- **UserRoles** — связь пользователей и ролей (многие-ко-многим)
- **RolePermissions** — связь ролей и разрешений (многие-ко-многим)

#### Логика работы

```
User → UserRole → Role → RolePermission → Permission → Resource
```

- Пользователь может иметь несколько ролей
- Роль может иметь несколько разрешений
- Разрешение определяет действие на конкретном ресурсе

#### API для управления правами

Должен быть реализован API с возможностью получения и изменения правил доступа (только для администраторов):
- CRUD операции для ролей, ресурсов, разрешений
- Назначение ролей пользователям
- Назначение разрешений ролям

#### Коды ответов

- **401 Unauthorized** — пользователь не авторизован (нет токена/невалидный токен)
- **403 Forbidden** — пользователь авторизован, но не имеет доступа к ресурсу
- **200/201** — успешное выполнение

### 3. Mock-объекты бизнес-приложения

Создать минимальные mock-представления ресурсов, к которым применяется система авторизации:

- Не требуется создавать таблицы в БД
- Реализовать Mock-View, возвращающие:
  - Список объектов при наличии прав
  - Ошибку 401/403 при отсутствии доступа

Примеры ресурсов:
- Документы (`/api/documents/`)
- Отчеты (`/api/reports/`)

## Технологический стек

**Рекомендуемый:**
- **Backend**: Django REST Framework
- **База данных**: PostgreSQL
- **Аутентификация**: JWT (JSON Web Tokens)

## Критерии оценки

Даже при неполной реализации проекта важно продемонстрировать понимание:

- Различий между аутентификацией и авторизацией
- Формирования JWT-токенов
- Принципов работы сессий
- Связи между запросами клиента и ответами сервера
- Механизмов login/logout
- Управления безопасностью приложения
